1. Neo4j       를 왜 써야 하는가
일반적인 DMS나 SQL DB는 다음 질문에 약합니다.
 1. 이 조항이 어느 쟁점과 연결되는가?
 2. 이 쟁점의 근거문서는 무엇인가?
 3. 이 사실관계는 어느 이메일, 회의록, 계약서에서 확인되는가?
 4. 이 리스크는 어느 보고서에 반영되었는가?
 5. 이 계약서 버전은 어느 마크업본을 대체하는가?
 6. 이 조항과 유사한 조항이 과거 어느 프로젝트에서 쓰였는가?
 7. 이 판례는 어느 의견서에서 인용되었는가?
 8. 이 Disclosure Schedule 예외는 어느 진술보장 조항을 제한하는가?
 9. 이 RFI 항목은 어느 리스크를 해소하기 위해 요청되었는가?
10. 이사회 의사록 부존재가 어떤 CP, 진술보장, 손해배상 조항에 영향을 주는가?

이런 질문들은 본질적으로 “관계”를 묻는 질문입니다. Neo4j 같은 그래프 DB가 적합한 이유가 여
기에 있습니다.
Law Firm OS의 차별성은 문서 저장이 아니라, 문서 간 의미 있는 법률관계의 추적입니다.

Neo4j 에는 원본 파일 자체가 아니라 다음을 저장합니다.

10. 문서 간 충돌
11. 유사 조항 관계
12. 후속 조치 관계

즉, Neo4j는 문서의 관계형 의미 계층입니다.

3.2. Neo4j   는 LLM Wiki의 백엔드가 되어야 함
앞서 말한 LLM Wiki는 사람이 보는 Markdown이 아니라 LLM이 읽기 좋은 구조화된 지식입니다.
그런데 LLM Wiki를 Markdown 파일로만 저장하면, 다음 질문에 약합니다.
 1. 이 쟁점을 뒷받침하는 모든 근거는?
 2. 이 조항과 관련된 모든 리스크는?
 3. 이 문서를 대체한 최신 버전은?
 4. 이 사실과 충돌하는 자료는?
 5. 이 Matter와 유사한 과거 Matter는?
 6. 이 판례가 인용된 모든 산출물은?
 7. 특정 회사가 등장하는 모든 딜은?
 8. 특정 정의어가 쓰인 모든 계약서 조항은?

이런 질문은 Neo4j가 더 적합합니다.
따라서 구조는 다음이 좋습니다.
계층                                     역할
Markdown/Obsidian View                 사람이 읽고 편집
LLM Wiki Page                          LLM   이 읽는 정리본

Raw Documents                          원문 근거
Citation Ledger                        주장별 근거 위치

즉, Neo4j에서 관계를 저장하고, LLM Wiki는 Neo4j 데이터를 읽어서 생성되는 뷰가 되어야 합
니다.

4. Neo4j      와 GraphRAG의 활용
4.1.   일반 RAG와 GraphRAG의 차이
일반 RAG는 “질문과 유사한 텍스트 chunk”를 찾습니다.
GraphRAG는 다음을 함께 사용합니다.

 1. 의미검색
 2. 엔티티 검색
 3. 관계 탐색
 4. 그래프 경로 추적
 5. 문서 간 연결
 6. 원문 citation
 7. 다중-hop 추론

Neo4j는 공식 GraphRAG Python 패키지를 제공하며, 해당 패키지는 graph search, vector
search, 외부 vector database와의 통합 retriever를 제공한다고 설명합니다.  Graph Databas… +1
Neo4j의 GenAI 문서도 GraphRAG, embeddings, vector indexes, GenAI plugin 등을 별도 영
역으로 제공하고 있습니다.           Graph Databas…



Law Firm OS에서 이 차이는 매우 큽니다.

예를 들어 사용자가 이렇게 묻습니다.
“이 SPA에서 매도인 입장에서 제8조 손해배상 조항이 위험한 이유를 알려줘.”

일반 RAG는 손해배상 조항 주변 chunk를 찾습니다.
GraphRAG는 다음 경로를 따라갑니다.

 1. Matter → HAS_DOCUMENT → SPA
 2. SPA → HAS_VERSION →  최신 버전
 3. SPA → CONTAINS_CLAUSE → 제8조 손해배상
 4. 제8조 → USES_DEFINED_TERM → “손해”, “위반”, “진술 및 보장”
 5. 제8조 → RELATES_TO_ISSUE → 진술보장보험, liability cap, 특별손해
 6. 제8조 → RELATES_TO_ISSUE → Disclosure Schedule 예외
 7. Issue → SUPPORTED_BY → 상대방 이메일, 회의록, 마크업
 8. Issue → SIMILAR_TO → 과거 유사 프로젝트 조항
 9. Risk → MITIGATED_BY → 수정안 후보
10. WorkProduct → BASED_ON → 검토의견서 초안

이 결과를 LLM에 넣으면 답변 품질이 훨씬 좋아집니다.

index는 노드나 속성을 벡터로 표현하여 유사도 검색과 분석 쿼리를 가능하게 하고, 임베딩을 사
용한 유사 노드·관계 검색에 활용됩니다.                    Graph Databas… +1

6. Neo4j    를 활용한 주요 기능
6.1.   유사 조항 검색

처리 방식:
 1. Clause 중 clauseType = Indemnity 검색
 2. partyFriendly = Seller 필터
 3. embedding 유사도 검색
 4. 과거 프로젝트별 사용 사례 탐색

 7. 최종 추천

단순 문구 검색보다 훨씬 낫습니다. “손해배상”이라는 단어가 없어도 indemnity 구조가 유사한 조
항을 찾을 수 있습니다.

Matter → Issue → Fact → Citation → Document

추가로 다음도 확인합니다.
Issue → Risk
Issue → RFIItem
Issue → WorkProduct
Issue → Authority
Issue → Task

그 결과 사용자는 다음을 봅니다.

 2. 근거 문서

 4. 관련 법령
 5. 미제출 자료
 6. 보완 필요 조치
 7. 보고서 반영 여부

이것이 Law Firm OS에서 매우 중요합니다.

6.3. RFI   자동 생성 및 추적
실사에서 자주 발생하는 흐름입니다.
 1. 문서 업로드
 2. Issue 자동 생성
 3. Issue별 미확인 사항 추출
 4. 미확인 사항을 RFIItem으로 변환
 5. RFI 제출 여부 추적
 6. 제출자료가 들어오면 해당 Issue와 연결
 7. Issue 상태를 unresolved → partially resolved → resolved로 변경

Neo4j 관계 예시는 다음과 같습니다.

Issue REQUIRES_ACTION RFIItem
RFIItem REQUESTED_BY Lawyer
RFIItem ANSWERED_BY Document
Document RESOLVES Issue
Document EVIDENCES Fact

이 구조가 있으면 RFI가 단순 엑셀 목록이 아니라, 리스크 해소 프로세스가 됩니다.
6.4.   계약서-회의록-이메일 정합성 검토
사용자 업무에서 자주 나오는 유형입니다.
질문:
“HTML 회의록이 계약서 원문과 녹취록에 부합하는지 검토해줘.”

Neo4j 구조를 쓰면 다음을 자동화할 수 있습니다.

 1. 회의록의 각 합의사항을 Fact 또는 NegotiationPosition 으로 추출
 2. 녹취록에서 같은 내용의 발언을 연결
 3. 계약서 조항에 반영되었는지 연결
 4. 이메일에서 후속 합의 여부 연결
 5. 불일치하면 CONTRADICTS 관계 생성
 6. 누락되면 NOT_REFLECTED_IN 또는 REQUIRES_ACTION 생성

결과적으로 다음과 같은 표를 자동 생성할 수 있습니다.
회의록 기재          녹취록 근거        계약서 반영        상태
합의됨             있음            반영됨           이상 없음
합의됨             없음            반영됨           회의록 근거 부족
합의됨             있음            미반영           계약서 반영 필요
미합의             있음            반영됨           계약서 과잉반영 가능성
상대방 요구          있음            미반영           협상 쟁점 유지

이건 일반 RAG만으로는 안정적으로 구현하기 어렵고, Neo4j가 들어가면 강해집니다.

10.2. Citation       없는 Fact 금지
Law Firm OS       에서 Fact 노드는 반드시 Citation과 연결되어야 합니다.

Fact without Citation = Draft Candidate, not Verified Fact

즉, citation이 없는 사실은 확정 사실로 쓰면 안 됩니다.
예외적으로 변호사가 직접 입력한 메모는 sourceType = lawyerMemo 로 관리할 수 있지만, 그
경우에도 작성자와 작성일을 남겨야 합니다.

clean                                   클린본

상태                              의미
reference                       참고용

LLM retrieval   시 기본값은 다음 순서여야 합니다.
 1. execution

 4. draft
 5. archived/reference

다만 사용자가 “마크업본 기준으로 검토”라고 하면 markup을 우선해야 합니다.

Neo4j 자체에 민감한 관계가 들어갑니다. 예컨대 특정 내부조사 자료, M&A 미공개 자료, 소송전
략 메모가 그래프에 연결될 수 있습니다.
따라서 Law Firm OS에서는 다음 접근제어가 필요합니다.
 1. Matter 단위 권한
 2. Client 단위 권한
 3. Document 단위 권한
 4. Node label 단위 권한
 5. Edge type 단위 권한
 6. Work product 권한
 7. Privileged note 권한
 8. External sharing 금지 플래그
 9. AI 처리 허용 여부
10. 외부 API 전송 금지 플래그

특히 privileged = true 또는 externalAIAllowed = false 인 자료는 Gemma 로컬 처리만
허용하고 외부 API로 보내면 안 됩니다.

장, Obsidian은 뷰 또는 에디터가 맞습니다.

14. Neo4j           를 쓰면 특히 강해지는 Law Firm OS 기능
14.1. “  왜 그렇게 판단했는지” 설명 가능
LLM 답변이 다음처럼 바뀝니다.
일반 답변:
“이 조항은 매도인에게 불리합니다.”

Neo4j 기반 답변:

“이 조항은 매도인에게 불리합니다. 이유는 ① 제8.1조가 진술보장 위반에 대한 손해배상 범위를
직접손해로 제한하지 않고 있고, ② 제8.3조의 cap 예외에 고의·중과실 외에도 특정 조항 위반이
포함되어 있으며, ③ Disclosure Schedule의 예외가 제5조 전체가 아니라 일부 진술보장에만 연
결되어 있고, ④ 과거 유사 프로젝트에서는 동일 구조에서 cap carve-out을 축소한 바 있기 때문
입니다.”
이 답변은 조항, 예외, 과거 샘플, 리스크가 그래프로 연결되어야 나옵니다.

14.2.   미확인 사항을 자동으로 드러냄
법률업무에서는 확인된 것보다 “아직 확인되지 않은 것”이 더 중요할 때가 많습니다.
Neo4j는 다음을 뽑을 수 있습니다.

 1. Issue는 있는데 Citation이 없는 항목
 2. Risk는 있는데 Mitigation이 없는 항목
 3. RFI는 있는데 Answer Document가 없는 항목
 4. CP 는 있는데 Evidence가 없는 항목
 5. Clause는 있는데 DefinedTerm 정의가 없는 항목
 6. Disclosure 예외는 있는데 관련 진술보장 조항 연결이 없는 항목
 7. WorkProduct에 인용된 Fact 중 reviewStatus가 unreviewed인 항목

이것이 실무적으로 매우 강합니다.

Neo4j 기반 Matter Graph Engine

분석으로 사용되지 않는다. Matter Graph는 LLM Wiki, RAG, 계약서 검토, 실사보고서 작성, RFI
추적, 회의록 정합성 검토 및 과거 자문사례 재사용 기능의 공통 기반으로 사용된다.

초안 생성에 활용하는 Local AI Worker로 배치한다.
넷째, Neo4j는 문서, 당사자, 사실관계, 조항, 정의어, 쟁점, 리스크, 근거,
자료요청, 협상 입장, 산출물 간 관계를 저장하는 Matter Graph Engine
으로 사용한다.
다섯째, 최종 법률판단, 계약서 작성, 의견서 작성, 판례·법령 적용, 협상전
략 수립은 Gemma 4 12B 단독이 아니라 Strong LLM, 검색 시스템,
Citation Ledger, 변호사 검토가 결합된 구조에서 수행한다.




제2장. 전체 제품 비전
2.1.   제품 정의
         는 로펌 또는 법률자문 조직이 수행하는 M&A, 투자, 기업
Law Firm OS
자문, 분쟁, 소송, 주주간계약, 실사, 계약서 검토, 회의록 검토, 자료요청,
보고서 작성 업무를 통합 관리하는 업무 운영체제이다.
본 고도화 사양에 따른 Law Firm OS는 다음과 같이 정의된다.
Law Firm OS는 각 Matter별로 원본문서, 문서 버전, 당사자, 사실관계,
계약조항, 정의어, 법률쟁점, 리스크, 근거자료, 자료요청, 협상경위, 법령·
판례·문헌, 산출물을 구조화하고, 그 관계를 Neo4j 기반 Matter Graph로
저장하며, 이를 바탕으로 LLM Wiki, GraphRAG, 계약서 검토, 실사보고
서 작성, 회의록 정합성 검토, RFI 추적, 과거 자문사례 재사용을 수행하
는 법률지식 운영체제이다.
2.2.   제품의 차별화 방향
기존의 일반적 DMS 또는 사건관리 시스템은 파일, 일정, 업무, 청구, 고
객정보 관리에 중점을 둔다. 그러나 로펌 실무에서 고부가가치가 발생하
는 지점은 문서 저장이 아니라 다음 질문에 답하는 능력이다.
 1. 이 쟁점은 어느 문서에서 비롯되었는가?
 2. 이 사실관계는 어느 이메일, 회의록, 계약서, 별지에서 확인되는가?
 3. 이 조항은 어느 리스크와 연결되는가?
 4. 이 리스크는 보고서와 계약서에 반영되었는가?
 5. 이 RFI 항목은 어떤 쟁점을 해소하기 위해 요청되었는가?
 6. 이 계약서 버전은 어느 마크업본을 대체하는가?
 7. 이 회의록 기재는 녹취록과 계약서 원문에 부합하는가?
 8. 과거 유사 거래에서 같은 조항을 어떻게 수정했는가?
 9. 특정 판례 또는 법령은 어느 의견서에서 인용되었는가?
10. 현재 Matter에서 아직 근거가 확인되지 않은 주장은 무엇인가?

본 고도화 사양의 핵심은 Law Firm OS가 위 질문에 자동 또는 반자동으
로 답할 수 있게 하는 것이다.

제3장. 핵심 설계 원칙
3.1. Matter-Native   원칙
모든 데이터는 Matter를 중심으로 관리한다.
Matter는 단순 폴더가 아니라 다음 정보를 포괄하는 최상위 작업 단위이
다.
 1. 고객
 2. 자문 포지션
 3. 거래 또는 사건 유형
 4. 당사자
 5. 담당 변호사
 6. 원본문서
 7. 문서 버전
 8. 사실관계
 9. 계약조항
10. 쟁점
11. 리스크
12. 자료요청
13. 협상경위
14. 법령·판례·문헌
15. 산출물
16. 후속 업무

Matter를 중심으로 하지 않고 Client, Document, Task, Email 등을 개별
적으로 관리하면 Law Firm OS는 단순 협업툴에 가까워진다. 반대로
Matter를 중심으로 모든 정보가 연결되면 해당 Matter의 법률적 상태를
하나의 그래프로 파악할 수 있다.
3.2. Raw Document       우선 원칙
LLM Wiki  와 Matter Graph는 원본문서를 대체하지 않는다.
모든 분석, 요약, Fact, Issue, Risk, Clause, Work Product는 원본문서
와 citation으로 연결되어야 한다. 원문 근거 없는 Fact는 확정 사실이 아
니라 후보 사실로만 취급한다.
원칙은 다음과 같다.
Fact without Citation = Draft Candidate, not Verified Fact.

즉, citation이 없는 사실은 AI가 생성한 후보 정보일 뿐이며, 변호사가 명
시적으로 확인하기 전까지 법률검토 결과나 외부 제출 산출물에 확정적
으로 사용해서는 안 된다.
3.3. AI   후보 생성 및 변호사 확정 원칙
Gemma 4 12B  또는 Strong LLM이 생성한 모든 노드와 관계는 기본적
으로 candidate 상태로 저장한다.
AI가 생성할 수 있는 후보는 다음과 같다.

 1. 문서 유형 후보
 2. 당사자 후보
 3. 날짜 후보
 4.  조항 구조 후보
 5. 정의어 후보
 6. 사실관계 후보
 7. 쟁점 후보
 8. 리스크 후보
 9. RFI 후보
10. 유사 조항 후보
11. 협상 입장 후보
12. 회의록 불일치 후보

변호사가 확인하면 confirmed 상태로 변경한다. 변호사가 반려하면
rejected 상태로 변경한다. 검토되지 않은 AI 후보는 외부 산출물의 확정
근거로 사용하지 않는다.
3.4. Version Priority   원칙
법률문서에서는 버전 혼동이 치명적이다. 따라서 모든 문서는 다음 상태
중 하나를 가져야 한다.
 1. draft
 2. markup
 3. clean
 4. execution
 5. superseded
 6. reference
 7. disputed
 8. archived

기본 retrieval 우선순위는 다음과 같다.
 1. execution
 2. latest clean
 3. latest markup
 4. draft
 5. reference
 6. archived

다만 사용자가 특정 버전을 명시한 경우에는 해당 버전을 우선한다. 예를
들어 “마크업본 기준으로 검토”라고 요청하면 markup 버전을 우선해야
한다.
3.5. Human-Readable + Machine-Readable   병행 원칙
         의 지식 구조는 사람이 읽기 좋은 형태와 기계가 질의하기
Law Firm OS
좋은 형태를 동시에 가져야 한다.
 1. 사람이 읽는 형태: Matter Wiki, Markdown/MDX, Obsidian-
       compatible export
 2.    기계가 질의하는 형태: Neo4j Graph, Vector Index, Citation
       Ledger
      이 읽는 형태: LLM Wiki Page, Retrieval Context Bundle
 3. LLM
 4. 변호사가 검토하는 형태: Review Queue, Diff View, Citation
       Panel

하나의 형태만으로는 부족하다. Markdown만 있으면 관계 질의가 약하
고, Graph만 있으면 사람이 편집하기 어렵다. 따라서 Neo4j가 원천 관계
저장소가 되고, Matter Wiki는 그 위에서 생성되는 편집·검토용 뷰가 되어
야 한다.

    표시되어야 한다.

제14장. 운영정책
14.1. 데이터 보존정책

Matter별 데이터는 다음 보존정책을 적용한다.
 1. Active Matter: 전체 데이터 활성 유지
 2. Closed Matter: 읽기 전용 보관
 3. Archived Matter: 검색 가능하되 수정 제한
 4. Litigation Hold Matter: 삭제 금지
 5. Client Deletion Request Matter: 법률상 보존의무 검토 후 처리
 6. Privileged Matter: 별도 암호화 및 접근로그 강화

14.2. AI   사용정책
 1. 외부 LLM 사용 가능 여부는 Matter 및 Document 단위로 관리한다.
 2. highly confidential 또는 privileged 문서는 기본적으로 Local AI만
    사용한다.
 3. 외부 LLM 사용 시 전송 데이터와 prompt를 기록한다.
 4. 외부 LLM에 전송된 문서·chunk·citation 범위를 추적한다.
 5. 사용자는 AI 답변의 근거 citation을 확인할 수 있어야 한다.
 6. AI가 생성한 결과는 변호사 검토 전 확정 산출물로 취급하지 않는다.

14.3. Knowledge Reuse      정책
과거 Matter의 지식 재사용은 다음 조건을 충족해야 한다.
 1. 해당 Matter에 대한 접근권한이 있어야 한다.
 2. 고객 기밀 또는 이해상충 제한을 준수해야 한다.
 3. privileged 자료는 권한 있는 사용자에게만 표시되어야 한다.
 4. 외부 고객에게 과거 Matter 명칭 또는 민감정보가 노출되어서는 안
    된다.
 5. 조항 문구 재사용 시 source Matter의 민감정보를 제거해야 한다.
 6. 과거 법률의견 재사용 시 법령·판례 최신성을 재확인해야 한다.

         제16장. 핵심 결론
         본 사양의 핵심은 Law Firm OS를 단순한 업무관리·문서관리 시스템이
         아니라, Matter 중심의 법률지식 그래프 시스템으로 전환하는 것이다.
         Obsidian은 사람이 이해하고 편집하기 쉬운 지식 연결 방식을 제공한다.
         LLM Wiki는 LLM이 자료를 검색이 아니라 추론 방식으로 읽도록 만드는
         구조를 제공한다.
         Gemma 4 12B는 기밀자료를 외부로 보내지 않고 로컬에서 1차 구조화
         하는 역할을 한다.
         Neo4j는 문서, 사실, 조항, 쟁점, 리스크, 근거, 산출물 간 관계를 저장하
         는 핵심 Matter Graph Engine이 된다.
         최종 구조는 다음과 같이 정리된다.
         Raw Documents는 DMS 또는 Object Storage에 저장한다.
         문서의 의미와 관계는 Neo4j에 저장한다.
         LLM Wiki는 Neo4j와 Citation Ledger를 바탕으로 생성한다.
         Gemma 4 12B는 로컬에서 후보 노드와 후보 관계를 생성한다.
         Strong LLM은 GraphRAG와 Citation Ledger를 바탕으로 고난도 분석
         과 작성에 사용한다.
         변호사는 AI 후보와 citation을 검토하여 확정한다.
         이 구조가 구현되면 Law Firm OS는 로펌 업무의 핵심 자산인 문서, 사실
         관계, 쟁점, 조항, 법리, 리스크, 산출물을 축적·재사용·검증 가능한 방식으
         로 운영할 수 있다.


위 사양에서 가장 먼저 개발해야 하는 것은 Neo4j 전체 고도화가 아니라 “Matter–Document–
Issue–Risk–Citation” 최소 그래프입니다. 이 최소 그래프가 없으면 LLM Wiki도 단순 요약문
서에 그치고, Obsidian export도 예쁜 노트 묶음에 그칠 가능성이 큽니다.
개발 우선순위를 더 압축하면 다음 5개입니다.
1. Citation Ledger
2. Document Register
3. Matter Graph   최소 스키마
 4. AI Review Queue
 5. Matter Wiki / Obsidian-compatible export

이 5개가 먼저 잡히면 이후 Gemma 4 12B, LLM Wiki, GraphRAG, Clause Library,
Negotiation Ledger를 얹는 구조가 안정적으로 됩니다.

    능할 것
10. 제품 사용량, AI 사용량, 변호사 생산성, 업무 리스크를 계량화할 수
    있을 것
1.3.   제품의 핵심 차별성
상위 SaaS 시장에서 단순 DMS, 단순 AI 챗봇, 단순 문서 자동화 도구는
장기적으로 차별성이 약하다.
Law Firm OS의 차별성은 다음이어야 한다.

 1. Matter-native architecture
       모든 데이터가 Matter를 중심으로 구조화된다.
 2. Legal Knowledge Graph
       문서, 사실, 조항, 쟁점, 리스크, 근거, 산출물이 Neo4j 기반 그래프로
       연결된다.
 3. Citation-first AI
       AI   답변과 산출물은 원문 근거와 연결된다.
 4. Human-in-the-loop legal review
       AI가 생성한 정보는 후보 상태로 저장되고 변호사 검토 후 확정된다.
 5. Workflow-native AI
        가 독립 챗봇이 아니라 SPA 검토, LDD, SHA 작성, RFI, 회의록
       AI
       검토, 소송 사실관계 정리 등 실제 업무흐름 안에서 작동한다.
 6. Hybrid AI routing
                등 로컬 모델, 외부 Strong LLM, 룰 엔진, 검색 엔진
       Gemma 4 12B
       을 자료 민감도와 업무난이도에 따라 분리 사용한다.
 7. Obsidian-compatible knowledge export
       사용자가 Matter Wiki와 내부 지식자료를 Markdown 기반으로 내보
       내고, 필요 시 Obsidian식 지식작업에 연결할 수 있다.
 8. Enterprise governance
       권한, 보안, 감사, ethical wall, data residency, retention, litigation
       hold를 제품의 중심에 둔다.

제17장. 최종 업데이트 결론
최상위급 SaaS로 만들기 위해 Law Firm OS는 다음 방향으로 업데이트
되어야 한다.
첫째, 제품의 중심을 단순 DMS 또는 AI 챗봇이 아니라 Legal
Knowledge Work Platform으로 재정의한다.

둘째, Obsidian형 Matter Wiki는 사용자 친화적 지식 뷰로 제공하되, 원
천 데이터는 Neo4j Matter Graph와 Citation Ledger에 둔다.
셋째, LLM Wiki는 요약문이 아니라 LLM이 reasoning할 수 있는 구조화
지식 레이어로 설계한다.
넷째, Gemma 4 12B는 로컬 기밀문서 처리, 문서 분류, 메타데이터 추출,
Fact/Issue/Risk 후보 생성에 사용하고, 최종 법률판단은 Strong LLM과
변호사 검토를 결합한다.
다섯째, Neo4j는 단순 그래프 시각화가 아니라 제품의 핵심 데이터 엔진
이 되어야 한다.
여섯째, Word Add-in과 Outlook Add-in은 필수이다. 변호사는 웹앱보다
Word와 Outlook에서 실제 업무를 수행하므로, 최상위 SaaS가 되려면
작업 환경 안으로 들어가야 한다.
일곱째, Enterprise SaaS로 판매하려면 SSO, SCIM, MFA, ethical
wall, DLP, audit log, data residency, customer-managed key,
                      가 필수이다.
retention, litigation hold

여덟째, 제품은 단일 기능 묶음이 아니라 workflow template, integration
marketplace, clause pack, practice area pack, jurisdiction pack을 제
공하는 플랫폼으로 진화해야 한다.
아홉째, 제품 성공의 핵심 지표는 “AI 답변 생성 수”가 아니라 citation 정
확도, 변호사 승인률, 업무시간 단축, 리스크 누락 감소, 지식 재사용률이
어야 한다.
최종적으로 Law Firm OS는 다음 구조를 목표로 한다.
Raw Documents는 안전하게 저장한다.
Matter Graph는 문서의 의미와 관계를 저장한다.
Citation Ledger는 모든 주장과 근거를 연결한다.
LLM Wiki는 AI와 변호사가 함께 읽는 구조화 지식층이 된다.
Gemma 4 12B는 로컬 처리 worker가 된다.
Strong LLM은 GraphRAG와 결합해 고난도 분석과 작성을 수행한다.
Word와 Outlook Add-in은 변호사의 실제 작업면을 장악한다.
Enterprise Governance는 고객 신뢰와 대형 계약의 전제가 된다.
Marketplace와 Workflow Builder는 제품을 장기 확장 가능한 SaaS 플
랫폼으로 만든다.
